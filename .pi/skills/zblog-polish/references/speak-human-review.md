# 「说人话」校对：zblog 适配版

参考项目：[Raymondhou0917/speak-human-tw](https://github.com/Raymondhou0917/speak-human-tw)，本次读取版本为 1.4.0，重点参考 `SKILL.md`、`references/patterns.md` 和 `references/humanize.md`。

以下是为 zblog 重新归纳的校对规则，不是上游完整副本或运行时调用。保持可离线使用；不自动下载或追随上游更新。

## 适配说明

- 保留简体中文和 Henry 的用语，不执行台湾词汇替换。
- 按用户确认的项目工作流直接交稿；不采用上游默认的两轮确认清单。用户要求“先标问题”时只提建议，不改稿。
- 不机械套用词频上限、标点配额或评分。具体事实和用户指定结构比表面形式重要。
- 不将本文变成 AI 内容鉴定器；这些是编辑启发，不是判断作者身份的证据。

## 校对顺序

先核对事实，再删无用表达，最后调整节奏。不要为了让文章更像人写的而改变含义。

### 1. 删除没有信息的句子

检查宏观开场、提前宣布“接下来会讲什么”、夸赞读者、万能总结和泛泛展望。删掉后不损失信息，就不必补一句替代品。

例如“这标志着 Agent 迈入全新时代”，应回到实际变化：新增了哪些机制？如果前文已经说过，就直接删掉。

### 2. 用具体动作替代抽象评价

“强大、灵活、可靠、无缝”单独出现不解释任何事情。写出它如何工作、什么时候生效；没有依据就不下这个结论。

“原子更新”可以解释为“同一事务中的修改要么一起保存，要么都不保存”，无需另造比喻。

### 3. 避免刻意制造深度与亲近感

- 不在每段结尾硬加一句格言。
- 不反复用“不是 A，而是 B”给普通区别增加戏剧感；真正需要的对比可以保留。
- 不加“说真的”“说到底”“我愣了一下”等虚构坦白或反应。
- 不用“我也没想清楚”表演不确定；有实际疑问才写疑问。

### 4. 不让格式压过内容

有步骤、并列项或对比时可以用列表；用户明确要求逐项列出时必须保留。不要机械把列表改散文，也不要把每句话都拆成小标题。

避免整句加粗、密集 emoji、长串短句和重复解释。段落可以长短不同，不为对称凑第三点。

### 5. 不用换词掩盖空话

删除“赋能”后不能补“加持”；删掉“革命”后不能换成“里程碑”。同一概念保持稳定称呼，重复准确术语比轮换模糊代称更清楚。

### 6. 保留责任边界

不能为了利落而删掉重试条件、适用范围、数据来源、风险或因果限制。例如“只有安全的工具才会重跑”不能缩成“所有任务自动重跑”。

泛泛的版本免责声明可以按用户要求删除，但正文不能因此暗示未验证的稳定性或能力。

## 交稿前检查

- 数字、链接、引用、专有名词与事实条件是否保留？
- 是否编造了作者观点、经历、产品效果或测试结论？
- 新增例子是否明确是假设示例，且符合事实？
- 是否把同一个结论重复讲了两遍？
- 是否有删掉也不损失信息的开头或结尾？
- 是否遵守用户的篇幅、结构和全文返回要求？
- 是否在未经授权时改动了文件？
